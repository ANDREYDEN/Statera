## General Guidelines

- prefer writing widget tests that simulate real user interaction with as little mocking as possible.
- write service unit tests to test edge cases and failure scenarios; don't duplicate widget tests that already cover the same test scenarios.
- keep the tests at the top of the file and place helper methods AFTER all of them, as top-level functions below `main()`. Don't declare helpers inside `main()`/`group()`, even when they need state from `setUp`.
- helpers must not close over test state: pass what they need (`tester`, `firestore`, ids, etc.) as parameters, with the `WidgetTester` first. Use named parameters for values that are not obvious at the call site, e.g. `getBalance(firestore, groupId: 'owing')`.
- declare constants shared by the tests and helpers (e.g. user ids) at the top of the file, above `main()`.

## Widget Tests

- use `customPump()` from `test/helpers.dart` to pump a widget under test.
- pass any providers (including Cubits/Blocs) via `extraProviders`.
- stub/mock only the required dependencies of the widget under test. The test should fail if any mock is removed.
- for `BlocListener`-driven widgets, stub `state` and/or `stream` depending on what is being used in the widget:

  ```dart
  when(cubit.state).thenReturn(SomeState());
  ```

  ```dart
  when(cubit.stream).thenAnswer((_) => Stream.value(SomeState()));
  ```

- mocks are generated by Mockito — each service class has `@GenerateNiceMocks([MockSpec<T>()])` on it and a corresponding `.mocks.dart` file. After adding a new mock annotation, regenerate with `dart run build_runner build`.
- always extract a helper method that pumps the widget under test, it should be named `pump[WidgetName]` and take the `WidgetTester` as its first parameter (e.g. `pumpContactPage(tester, firestore)`).
- for flows that touch repositories, prefer a `FakeFirebaseFirestore` with the real repositories (provided via `extraProviders`) over mocks, seed the data with `seed[Thing]` helpers and assert on the resulting documents.

## Service Unit Tests

- ensure that only one service method is called per test - the method under test; to test how multiple service methods interact together, write a widget test that uses the service instead.

## BLoC Tests

- BLoC-unit tests use the `bloc_test` package (`blocTest<>`, `seed:`, `act:`, `expect:`).
